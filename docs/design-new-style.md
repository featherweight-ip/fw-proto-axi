# fw-proto-axi, new style: design (draft for review)

Status: **draft, 2026-11-11.** Nothing implemented yet. Inputs: `axi4-package-brief.md`
(the brief), `../../featherweight-hdl/fw-hdl-sv-weave/abstractors.md` and
`protocol-ports.md`, the existing package in this repo, and sv-weave
(`packages/sv-weave` in the fw-hdl-sv-weave packet).

This is the first of a family of protocol packages in the new style. Every decision
below is meant to carry over to the next protocol, so the generators are protocol-agnostic
and live outside this package (§6).

## 1. Principle: a minimal core, everything else derived

A protocol package has two kinds of source:

- **The core specification**, written by hand. It holds only the facts a person has to
  decide: the parameters, the channel payloads, how the channels form a port, the
  transaction-level API, and the protocol rules. It contains no forwarding, no
  registration and no field list written twice.
- **Derivatives**, generated by sv-weave weavers from the core: base classes for every
  interface class, listener interfaces, proxies, fan-outs, channel APIs, struct-port field tables, pack/unpack, bridges,
  abstractor glue, pin-map presets and, later, the pyhdl-if API definition.

There is also behavioural code that cannot be derived but is not specification: the
manager and subordinate adapters (transaction ↔ beats, per-ID ordering), the memory
model and the rules' bodies. It is written by hand on top of the derived classes, and is
kept small by using them.

The test of the split: **adding a field to a channel, or a method to an API, should be a
one-line change to the core** that reaches the pins, the pack/unpack, the listeners, the
monitor and the pin maps without further edits.

### What this removes from today's package

| Today (hand-written or macro) | New style |
|---|---|
| `axi4_proto_macros.svh`: `FW_AXI4_{MGR_SOCKET,SUB_MIRROR,XACT}_IMP` | Generated imp/proxy classes (§4.2, §4.4) |
| `axi4_wire.svh`: pack/unpack for each channel, field order written twice | Gone. Beats are exact-width packed structs, so packing is a cast (§3.2) |
| Field lists repeated in `axi4_types_pkg` `*_bits()`, `axi4_mon_msg.sprint`, `axi4_cfg::mask_*` | One struct per channel. `$bits`, sprint and compare are derived |
| `axi4_cfg` (run-time widths, masking) | Gone. Widths are static class parameters |
| `axi4_mon_fanout`, `axi4_mon_msg` (tagged per-channel holder) | Generated listener fan-out. The monitor API *is* the listener interface (§4.1) |
| `axi4_l1_endpoints` `clear()`/`idle()` listing the channels | Generated from the bundle |
| `axi4_xtor_bridges.svh` (one send/recv loop per channel) | Generated from the bundle (§4.5) |
| AXI-specific `xtor_if`/core/xtor RTL | Five instances of the generic rv transactor, wired by a generated wrapper (§5) |

## 2. Parameterization

**Decision (proposed): one parameter-struct value, `axi4_param_t P`, on every class and
module.** The same struct value parameterizes the RTL (as today, `parameter axi4_param_t P`)
and the class layer, so the emitter writes `#(P)` in both and they cannot disagree.

```systemverilog
typedef struct packed {
    int unsigned ADDR_W, DATA_W, ID_W;
    int unsigned AWUSER_W, WUSER_W, BUSER_W, ARUSER_W, RUSER_W;   // 0 = absent
    bit          HAS_QOS, HAS_REGION;                              // optional signals
} axi4_param_t;
```

The API methods are sized by `P`. Their arguments are typedefs derived from `P` (§3.2),
so a 48-bit-address port and a 32-bit one are different, statically checked types.

**Spike result (2026-11-11, scratchpad).** I compiled a struct-valued class parameter, with
beat typedefs sized from `P.ADDR_W`/`P.ID_W` inside a parameterized class, and an
interface class whose task signatures use those typedefs:
- **Verilator 5.055:** compiles and gives the right widths (`$bits` = 55 for 6+48+1).
- **xezim 0.11.3:** gives wrong widths for this form and for a `type P` form. Out of
  scope: Verilator is the target simulator.

**Why a struct value rather than `type P` (a params class) or a list of int parameters:**
- It is the same object the RTL already uses.
- It is one parameter, so every generated class gets the identical header `#(axi4_param_t P = AXI4_PARAM_DEFAULT)`. The weavers never have to work out a parameter list (see the sv-weave gap in §6.2).
- Adding a width means adding a struct member. No class headers change.

**Absent fields.** A zero-width field can't be declared, so an optional field is declared as
`logic [w1(P.AWUSER_W)-1:0] user` and marked as optional (§3.2). The field table leaves
it out when its width parameter is 0, so it has no pin, no transactor bits and no monitor
field. In the class layer it stays as one bit held at 0, as today.

## 3. The core specification

The core is about 250 lines in two packages, and is everything a reviewer of the protocol
needs to read. Each has a generated counterpart:

| | spec (hand-written) | impl (generated) |
|---|---|---|
| synthesizable, no classes | `fw_proto_axi4_defs_pkg`: §3.1 | `fw_proto_axi4_defs_pkg_woven`: payload widths; plus the transactors' RTL cores (§5) |
| classes | `fw_proto_axi4_core_pkg`: §3.2-3.4 | `fw_proto_axi4_core_pkg_woven`: §4 |

The split exists because RTL flows (sv2v, Yosys) cannot read a package that holds
classes. The bundle names its synthesizable package (`fw_defs_pkg`). A user of the
classes imports both spec packages; a woven package repeats its spec package's imports.

### 3.1 Parameters and encodings

In `fw_proto_axi4_defs_pkg`: `axi4_param_t`, `AXI4_PARAM_DEFAULT`, the burst/size/resp enums,
and the burst arithmetic functions (`beat_addr`, `crosses_4k`, `burst_legal`, …). These carry over from
`axi4_types_pkg` mostly unchanged. The maximum-width beat structs and `*_bits()` are
dropped.

### 3.2 Channel payloads

These are packed structs inside one parameterized class, so that they can depend on `P`.
Member names are the AMBA names without the channel prefix. The prefix comes from the
channel name in the bundle (§3.3). That is how AW and AR share one type.

```systemverilog
class axi4_types #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    typedef struct packed {
        logic [P.ID_W-1:0]                   id;
        logic [P.ADDR_W-1:0]                 addr;
        logic [7:0]                          len;
        axi4_size_e                          size;
        axi4_burst_e                         burst;
        logic                                lock;
        logic [3:0]                          cache;
        logic [2:0]                          prot;
        (* fw_opt = "HAS_QOS"    *) logic [3:0] qos;
        (* fw_opt = "HAS_REGION" *) logic [3:0] region;
        (* fw_opt = "user"       *) logic [w1(P.AXUSER_W)-1:0] user;  // AW/AR user widths: see Q3
    } ax_t;
    typedef struct packed { logic [P.DATA_W-1:0] data; logic [P.DATA_W/8-1:0] strb;
                            logic last; (* fw_opt = "user" *) logic [w1(P.WUSER_W)-1:0] user; } w_t;
    typedef struct packed { logic [P.ID_W-1:0] id; axi4_resp_e resp;
                            (* fw_opt = "user" *) logic [w1(P.BUSER_W)-1:0] user; } b_t;
    typedef struct packed { logic [P.ID_W-1:0] id; logic [P.DATA_W-1:0] data; axi4_resp_e resp;
                            logic last; (* fw_opt = "user" *) logic [w1(P.RUSER_W)-1:0] user; } r_t;
endclass
```

**Settled in implementation** (`src/core/fw_proto_axi4_core_pkg.sv`, plan D4/D5): AW and AR
are separate structs `aw_t`/`ar_t`, so each has its own user width. The attribute is
`(* fw_opt = "<P member>" *)`: the field has pins iff `P.<member> != 0` (so `HAS_QOS` and
`HAS_REGION` are `int unsigned` 0/1). IDs are `w1(P.ID_W)` wide, like the user fields,
and marked `fw_opt = "ID_W"`, so with no ID there are no ID pins.

### 3.3 The port bundle

The bundle names the channels, their direction relative to the manager, and the
handshake family. This one declaration is the struct-port type. It answers brief Q1 with
**a bundle of channel struct ports**: `connect()` takes the whole bundle, while the pin map,
monitors and rules see each channel.

```systemverilog
(* fw_proto_bundle = "axi4", fw_roles = "mgr,sub" *)
class axi4_bundle #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    typedef axi4_types #(P) t;
    (* fw_fwd *) fw_rv_ch #(t::ax_t) aw;
    (* fw_fwd *) fw_rv_ch #(t::w_t)  w;
    (* fw_rev *) fw_rv_ch #(t::b_t)  b;
    (* fw_fwd *) fw_rv_ch #(t::ax_t) ar;
    (* fw_rev *) fw_rv_ch #(t::r_t)  r;
endclass
```

`fw_rv_ch` is the ready/valid family from fw-hdl. It contributes `valid` (fwd) and `ready`
(rev), plus the signal-level rules (valid held until ready, payload stable while stalled,
no X on valid). The derived pin names are `<channel><family-signal>` and
`<channel><member>`: `awvalid`, `awready`, `awaddr`, `wstrb`, … These are the AMBA names.

AXI's cross-channel facts (`len+1` W beats per AW, B after the last W, ID matching) are
**not** in the bundle. They are rules (§3.5). The `relations()` strings proposed in
`protocol-ports.md` aren't needed.

### 3.4 The transaction-level APIs

These are the only APIs written by hand. The channel-level APIs are derived from the bundle
(§4.3). There are two (decided after P5, see `p5-open-issues.md`):

**`axi4_burst_req_if` / `axi4_burst_rsp_if`, the protocol's own API, in the channel
payload types (D11).** A transaction is its address beat, its data beats and its response
beat(s). Nothing on the channels is lost (per-beat RRESP, every USER field), and a field
added to a payload reaches it with no other edit, which meets the §1 test.

The API is two interfaces, one per direction, like the channel APIs: the manager calls
the request side, the subordinate calls the response side back. A request returns once its
beats are accepted, not when it completes; responses arrive as calls, as they complete,
out of order across IDs as AXI allows. No thread waits per outstanding transaction. Only
the transactor bridges wait (their receive loops, against the pins).

```systemverilog
(* fw_api *)
interface class axi4_burst_req_if #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    typedef axi4_types #(P)::aw_t aw_t; ...  // local typedefs, see §6.2
    pure virtual task write_burst(input aw_t aw, input w_t w[$]);   // aw.len + 1 beats
    pure virtual task read_burst (input ar_t ar);
endclass
(* fw_api *)
interface class axi4_burst_rsp_if #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    pure virtual task write_resp(input b_t b);     // one per write_burst
    pure virtual task read_resp (input r_t r);     // one per R beat; r.last ends the burst
endclass
```

Rules:
- **A response may come inside its request.** A zero-delay target calls `write_resp`
  before `write_burst` returns. A caller is ready for its responses before it calls.
- **Response calls may block** (a beat accepted on the pins). A subordinate adapter
  queues them and sends from one loop per response channel, so a stalled B never holds up
  the loop that receives W.
- **Same ID, in order.** A target responds to one ID in request order (AXI A5/A6); R beats
  of different IDs may interleave.

The pair is carried by `axi4_burst_mgr_socket` (an `fw_socket`: calls req, provides rsp)
and `axi4_burst_sub_socket` (its `fw_mirror`). The adapters, the memory model and wrapped
IPs speak it. `axi4_burst_blocking` is a blocking convenience on top (a call per burst that
returns with its response, waiting on a per-ID queue), for test writers.

**`axi4_xact_if`, a convenience layer on top**, for test writers and Python: plain
arguments, no channel structs, blocking. It is implemented over the burst API by a shim
(`axi4_xact_on_burst`, on `axi4_burst_blocking`); `axi4_burst_on_xact` puts a plain-API
target behind the burst API, losing USER and per-beat responses, with a process per call
(a blocking target needs one).

```systemverilog
(* fw_api *)
interface class axi4_xact_if #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    pure virtual task write(input addr_t addr, input data_t data[$], input strb_t strb[$],
                            input attr_t attr, output axi4_resp_e resp);
    pure virtual task read (input addr_t addr, input int unsigned beats, input attr_t attr,
                            output data_t data[$], output axi4_resp_e resp);
endclass
```

`write` moves `data.size()` beats and `read` moves `beats` beats. `attr`
(`axi4_types::attr_t`: id, burst, size, lock, cache, prot, qos, region, user) holds the
address-channel fields. `resp` is B, or the worst R beat's.

Both follow the API conventions shared with fw-api-kit, which keep them pyhdl-if-friendly:
- a task when the call may block, a function otherwise;
- only `input`/`output` arguments: no `ref`, no events, no class handles in signatures;
- packed types and queues of packed types are allowed.

### 3.5 Rules

Rules are the protocol's contract (brief §5). Each one is a class extending a derived
listener base (§4.1), in the restricted form from `abstractors.md` §4a: immediate asserts,
`fw_count`/`fw_flag`, and `fw_any`. The rules are specification, so they stay hand-written.
The list is brief §5. They are designed in detail at milestone A3; this doc fixes only
their attachment point: **the listener interfaces of the channel APIs**.

## 4. Derivatives (generated)

Every derived class has the header `#(axi4_param_t P = AXI4_PARAM_DEFAULT)` and is emitted
into the woven package. `<api>` stands for any `(* fw_api *)` interface class, derived or
written by hand.

### Base class for every interface class: `<if>_base`

Every interface class gets a `virtual class <if>_base #(P) implements <if> #(P)`. This
covers the hand-written APIs, the derived channel APIs and the derived listener
interfaces. A client extends the base and overrides only the methods it cares about,
instead of implementing every pure virtual method. The SV restriction to single class
inheritance is not a problem: a client that needs two such interfaces extends one base
and implements the other directly, or uses two small member objects.

The default bodies depend on what kind of interface it is:

| Interface kind | Default body | Why |
|---|---|---|
| Listener (`<api>_listener`, every method a `void` function) | empty | Ignoring an event is always correct |
| API (`(* fw_api *)`, derived or hand-written) | error naming the class and method (`fw_error`, then return), outputs set to `'0` | A call that nobody implemented must not be dropped silently |

An attribute on the interface class or the method, `(* fw_default = "empty" *)` or
`"error"`, overrides the default for a case the table gets wrong. An example is an
optional API method that a stub may ignore.

Uses within this package:
- **Rules and monitors** extend `<api>_listener_base`.
- **Test stubs and partial models** extend `axi4_req_if_base`/`axi4_rsp_if_base`: for example, a read-only memory implements only `ar`.
- **Proxies and fan-outs** (§4.2) implement the interface directly, since they must cover every method.

### 4.1 Listener interface: `<api>_listener`

For each API method `m`: `<m>_pre` and `<m>_post`. The suffix (not a `pre_` prefix) keeps each operation's callbacks together when sorted.

```systemverilog
interface class axi4_req_if_listener #(axi4_param_t P = AXI4_PARAM_DEFAULT);
    pure virtual function void aw_pre (input ax_t t);     // the call was made / offered
    pure virtual function void aw_post(input ax_t t);     // the call completed / accepted
    ...
endclass
// plus axi4_req_if_listener_base, with empty bodies (see "Base class" above)
```

- **Callbacks are functions,** so a listener can't block or alter the call. That is required for rules to be evaluable in formal.
- **Arguments:**
  - `<m>_pre` receives the inputs.
  - `<m>_post` receives the inputs and the outputs; it is the event that rules normally annotate.
- **Meaning at each level:**
  - **On a proxy:** pre is called before forwarding and post after it returns.
  - **On a pin monitor:** pre is the first cycle with `valid`, and post is the handshake.

  This means the signal-level rules can be stated once, as "no `pre` without a matching
  `post` before the payload changes", and checked against either source.
- **The monitor role is not a separate API.** A monitor is a producer of listener calls, and anything that consumes monitor output implements the listener. This replaces `axi4_mon_if`, `axi4_mon_msg` and `axi4_mon_fanout`.

### 4.2 Proxy and fan-out: `<api>_proxy`, `<api>_listener_fanout`

```systemverilog
class axi4_req_if_proxy #(...) implements axi4_req_if #(P);
    axi4_req_if #(P)           m_target;
    axi4_req_if_listener #(P)  m_listeners[$];
    function void add_listener(axi4_req_if_listener #(P) l); ...
    virtual task aw(input ax_t t);
        foreach (m_listeners[i]) m_listeners[i].aw_pre(t);
        m_target.aw(t);
        foreach (m_listeners[i]) m_listeners[i].aw_post(t);
    endtask
    ...
endclass
```

- **The proxy is where the class layer is observed.** Inserted abstractors and handles expose one, so tests, monitors and rules attach to `dut.mem_abs` by path with no change to the description.
- **Listener types:** listeners are held as interface-class handles and never cast. The Verilator `$cast` issue (brief §8) does not arise.
- **`<api>_listener_fanout`:** implements the listener and forwards to a list, so one monitor source can feed several consumers.

### 4.3 Channel APIs: from the bundle

For a bundle with roles `mgr,sub`:
- **`axi4_req_if`:** the fwd channels, one `task <ch>(input <payload> t)` each (`aw`, `w`, `ar`). The task returns when the beat is accepted.
- **`axi4_rsp_if`:** the rev channels (`b`, `r`).
- **Role link types:** manager = port of `req`, export of `rsp`; subordinate = the mirror image. The socket and mirror typedefs are derived from these.

Because they are `(* fw_api *)` classes, §4.1 and §4.2 apply to them as well. The method
name equals the channel name. That is the only link a bridge needs between a method and
its pins.

### 4.4 Imp classes (replacing the `_IMP` macros)

The macros exist because SV cannot parameterize a method-name prefix (`m_imp.NAME_b`).
There are two derivations, in this order:
1. **Now:** `<api>_imp #(P, type IMP)` forwards to an `IMP` that implements the API
   itself. This covers components with one export per API type, which is every
   component in today's package.
2. **Later, with the fw binding** (§6.3): a class weaver on components. For each field of
   an export type it generates the nested forwarding class to `<field>_<method>`, exactly
   what the macro does today, but with no macro at the use site.

### 4.5 Struct port, field table, bridges, abstractor glue

All of these come from the bundle (§3.3):
- **The field table:** `field("awvalid",1,FWD)`, `field("awaddr",P.ADDR_W,FWD)`, …, with optional fields dropped.
- **The typed `link()`/`bind_inner()`.**
- **The `connect()` overloads that auto-insert the abstractor per role** (`<port>_abs`).
- **The abstractor's string tables** for the emitter (transactor module, vif type, bridge type, join statement, transactor pins).
- **Per-channel bridges:**
  - an outbound method is `vif[ch].send(t)`;
  - an inbound channel is a forked `recv → proxy.<ch>(t)` loop;
  - the monitor bridge calls `<ch>_pre`/`<ch>_post` on its listener.

  These replace `abs_lib.svh` lines 178-238 and 415-532 of the prototype and all of `axi4_xtor_bridges.svh`.

### 4.6 Pin-map presets

From the field table plus a naming style: `prefix("s_axi_")`, `prefix("m_axi_")`, and
upper case `S_AXI_` with upper-case field names. Wrapping a reference IP takes one line
per port (brief §6). The slices of packed-vector pins (crossbar) and SV struct pins (PULP)
are pin-map features, not derivatives; they are tracked in brief Q2.

### 4.7 Later

- the pyhdl-if API definition from each `(* fw_api *)` class;
- SVA property generation from the rules (A4).

Both read the same model the weavers already build.

## 5. RTL

- **No AXI-specific transactor RTL.** Each channel is an rv channel, so the transactors are
  five instances of fw-hdl's rv initiator/target/monitor transactor, with payload width
  `$bits(<payload>)`. A thin wrapper per role, generated from the bundle, splices the
  struct onto the AMBA pins.
- **The wrapper's synthesizable part is its own generated module**,
  `axi4_<role>_xtor_core`: the five fw-hdl rv cores and the splice, with the payloads as
  flat vectors in their structs' packing, sized by `axi4_<payload>_bits(P)` from
  `fw_proto_axi4_defs_pkg_woven`. It imports no class package, so sv2v and Yosys read it;
  `axi4_fv_ns` proves it back to back. `axi4_<role>_xtor` is that core plus the rv
  interfaces of the class side.
- **Backpressure and queue depth** stay per channel, configured by path (`dut.mem_abs.aw.stall_pct`).
- **`axi4_checker.sv` is retained as the signal-level reference** until the rule-generated properties (A4) match it. After that it becomes a generated artifact or is retired.
- **The register slice (`axi4_slice`) and its proof** carry over unchanged.

This needs fw-hdl's rv transactors to take run-time stall settings and a run-time queue
depth. Both are already listed in the brief (§8).

## 6. Generation mechanism (sv-weave)

### 6.1 Flow

```
core .sv  ──►  svweave.Weave (dfm)  ──►  fw_proto_axi4_core_pkg_woven  (listeners, proxies,
                 fw binding +                                         channel APIs, bridges,
                 fw-proto weavers                                     field tables, presets)
                                     ──►  fw_proto_axi4_pkg  (hand-written behaviour:
                                          adapters, mem model, rules; imports both)
```

- **The weavers are generic** (`fw-proto` weavers). They select by attribute: `has_attr("fw_api")`, `has_attr("fw_proto_bundle")`. Nothing in them names AXI.
- **sv-weave's `on_design` hook** walks the selected classes and inserts the class text into the `<pkg>_woven` package.
- **Generated output is not committed.** `weave-report.md` and the woven sources are build outputs that can be inspected (Q5).

### 6.2 sv-weave gaps and how the design avoids them

| Gap (today) | Effect | Approach |
|---|---|---|
| Members of a generic (unspecialized) class are not modelled; only used specializations are | A weaver can't read `axi4_req_if #(P)`'s methods generically | Weave from the default specialization. Every core class has the single `#(axi4_param_t P = …)` header, so the weaver re-emits that fixed header verbatim. **Proper fix:** model generic class members in sv-weave (preferred, small) |
| Specialized argument types print resolved, e.g. `axi4_types#('{32,…})::ax_t` | The generated text would be fixed to one width | **Rule:** core method signatures use only *class-local* typedef names (`ax_t`), which sv-weave prints bare. Each core and generated class declares the same local typedef block (emitted by the weaver) |
| Packed-struct members are not exposed (only type text) | No field table from `ax_t` | Read the struct through the pyslang `.slang` handle in the weaver (unstable API) until sv-weave models struct members and their attributes |
| Interface classes can't be weave targets | No woven subclass of an API | Not needed: listeners and proxies are new classes (`on_design`), not subclasses |
| Weavers can't write files or modules | No generated RTL wrapper (§5) | The binding's `init_files()` emits it, or a small Python generator in the dfm flow reads the same model |
| No fw binding | Config requires one; no factory registration | A minimal fw binding in fw-hdl (`python/fw/hdl/weave/`), needed anyway for §4.4 step 2 and for shells |

The sv-weave changes (generic members, struct members, class-scope typedefs) are small and
general. **They should be done in sv-weave rather than worked around in every weaver.**

### 6.3 Where the code lives

| What | Where |
|---|---|
| Core spec, hand-written behaviour, rules, tests | this repo |
| fw-proto weavers + fw binding | `fw_proto/` in this repo first (plan D2); moves to fw-hdl (`python/fw/hdl/weave/`) once a second protocol reuses it |
| `fw_rv_ch`, `fw_rule`/`fw_any`/`fw_count` | `fw_proto/src` first, then fw-hdl `src/std` |
| the rv transactors | fw-hdl `src/std` (changes on a branch of the `packages/fw-hdl` checkout) |
| sv-weave model extensions | `packages/sv-weave` checkout, on a branch (plan §8) |

## 8. Open questions for review

1. **Parameter struct.** Proposed: one `axi4_param_t P` value on every class and module
   (§2), verified in Verilator 5.055.
2. **Optional-field marking.** `(* fw_opt = "HAS_QOS" *)` on the member, naming the
   enabling parameter. The alternative is a convention that `w1(P.X)` widths are optional
   when `X == 0`, which needs no attribute but is implicit. I recommend the attribute.
3. **AW/AR user widths.** Sharing `ax_t` forces `AWUSER_W == ARUSER_W`. Options:
   (a) separate `aw_t`/`ar_t` (more core lines, no constraint);
   (b) parameterize `ax_t` by its user width.
   I recommend (b) if typedefs in a parameterized class can take it cleanly, otherwise (a).
4. **Transaction API shape.** `write`/`read` with plain arguments (§3.4, pyhdl-if-friendly)
   or keep the `axi4_xact` object? I recommend plain arguments for the API, with the object kept
   inside the adapters.
5. **Generated sources in git.** Build-time only (proposed), or committed with a CI
   freshness check so they can be reviewed in PRs?
6. **Pre/post at pin level.** Is "pre = first valid cycle, post = handshake" the meaning we
   want, or should a pin monitor emit only `post`?
7. **Repo.** Build the new style in this repo next to the old one (proposed, §7), or start
   in a fresh repo?
